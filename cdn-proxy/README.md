# VLESS через российский CDN

Схема для случая, когда прямой путь до зарубежного сервера перекрыт, а
российские адреса ходят свободно. Клиент подключается к узлу CDN внутри России —
снаружи это обычный HTTPS к Яндексу. CDN передаёт запрос на наш сервер, nginx по
секретному пути отдаёт его в Xray, а всё остальное отвечает безобидным сайтом.

За основу взята инструкция
[ServerTechnologies/proxy-via-russian-cdn](https://github.com/ServerTechnologies/proxy-via-russian-cdn)
с одним существенным отличием: там конфиг nginx пишется поверх `default` с
директивой `default_server`, что на сервере с уже работающими сайтами сносит их
все разом. Здесь добавляется отдельный виртуальный хост.

## Почему именно XHTTP

CDN умеет проксировать только HTTP и HTTPS — голый WireGuard через него не
пройдёт. Остаётся туннель поверх HTTP, и тут есть нюанс: изначально XHTTP гонял
данные методом POST, а его блокируют практически все CDN. В конце января 2026
года в Xray добавили `uplinkHTTPMethod`, позволяющий взять другой метод, обычно
GET. Поэтому **нужно ядро Xray новее 31.01.2026** — в старом такого параметра
нет, и схема не соберётся.

Важно: обновлять надо именно **ядро**, а не версию панели. 3x-ui и подобные — это
графическая надстройка, версии у них независимые.

## Что понадобится

- Домен с возможностью править записи A, CNAME и TXT.
- Сервер с белым IP, nginx и открытым портом 443. CDN ходит только на 443,
  другой порт указать нельзя.
- Аккаунт в Yandex Cloud с балансом в несколько сотен рублей.
- Свежее ядро Xray (см. выше) и свежие клиенты: Happ, v2rayNG, v2rayN,
  Shadowrocket. Параметр новый, старые сборки его не понимают даже после
  обновления приложения.

## Два имени

Нужны два доменных имени. Подойдут и два поддомена одного домена.

| Имя | Запись | Куда | Зачем |
|---|---|---|---|
| `origin.example.ru` | A | IP сервера | источник, его видит только CDN |
| `cdn.example.ru` | CNAME | технический домен Яндекса | этот адрес идёт в клиенты |

Клиент подключается к `cdn.example.ru`, видит сертификат Яндекса и ничего не
знает про `origin`. Яндекс обращается к `origin.example.ru` по HTTPS и
подставляет его же в заголовок `Host` — поэтому на сервере нужен свой
сертификат Let's Encrypt для имени источника.

## Порядок действий

### 1. A-запись на источник

У регистратора создай запись типа A: имя `origin`, значение — IP сервера. TTL
оставь по умолчанию.

Дождись, пока разойдётся:

```bash
getent ahostsv4 origin.example.ru
```

Пока не ответит нужным адресом, дальше идти нельзя: certbot получит отказ и
потратит попытку из недельного лимита Let's Encrypt. Обычно это занимает от
нескольких минут до получаса.

### 2. Источник

```bash
sudo bash cdn-proxy/setup-origin.sh \
  --domain origin.example.ru \
  --email me@example.ru \
  --port 8081 \
  --path /секретный/путь
```

Скрипт проверит A-запись и занятость порта, выпустит сертификат, положит
сайт-заглушку и напишет отдельный виртуальный хост. В нём три блока:

- `/health` — дешёвый ответ для опроса со стороны CDN;
- секретный путь — проксирование в Xray с полностью отключённой буферизацией
  (XHTTP держит длинные потоковые запросы, любая буферизация их ломает:
  данные копятся в nginx вместо того, чтобы идти клиенту);
- всё остальное — статика заглушки.

Если путь не задать, сгенерируется случайный. Предсказуемый вроде `/api/stream`
лучше не брать — его переберут.

Проверить, что получилось:

```bash
curl https://origin.example.ru/health
curl -o /dev/null -w '%{http_code}\n' https://origin.example.ru/
```

### 3. Входящее подключение в Xray

В панели: «Входящие» → добавить → вкладка «Расширенный шаблон». Удалить
дефолтный конфиг, вставить шаблон из инструкции, поправив два поля:

- `"port"` — порт из `--port` (не 8080, если на нём уже nginx);
- `"path"` в `xhttpSettings` — тот же путь, что в nginx.

Эти значения должны совпасть в трёх местах: nginx, Xray и клиент. Расхождение
в любом — и соединение не установится, причём без внятной ошибки.

Оставь `"listen": "127.0.0.1"`: Xray слушает только локально, снаружи к нему
попадает лишь то, что пропустил nginx по секретному пути.

Клиентов заводи по одному на устройство — тогда можно отозвать доступ у одного,
не трогая остальные.

### 4. Сертификат в Yandex Cloud

Нужен для имени, которое пойдёт в CNAME (`cdn.example.ru`), а не для источника.

1. Создать аккаунт, пополнить на 200–300 рублей.
2. «Создать ресурс» → Certificate Manager → «Добавить сертификат» →
   «Сертификат от Let's Encrypt».
3. В поле «Домен» — `cdn.example.ru`. Тип проверки — DNS.
4. После создания открыть сертификат, внизу будет «Проверка прав на домены».
   Выбрать TXT-запись и создать её у регистратора с предложенными именем и
   значением.

Проверка занимает 20–30 минут. Сертификат должен перейти в состояние «Выпущен».

### 5. CDN-ресурс

«Все сервисы» → Cloud CDN → «Создать ресурс».

- «Доменное имя источника», «Значение заголовка» и «Доменное имя» — везде имя
  источника (`origin.example.ru`).
- На шаге «Дополнительно» выключить выгрузку логов и экранирование.

После создания открыть ресурс, внизу раздел «Настройки DNS» — там технический
домен вида `xxxxxxxx.gslb.yccdn.ru`.

### 6. CNAME

У регистратора: имя `cdn`, тип CNAME, значение — технический домен из
предыдущего шага.

Настройки CDN и DNS применяются не сразу, закладывай 15–30 минут.

### 7. Клиент

Скопировать из панели **ссылку для подключения** (не ссылку на подписку) и
отредактировать:

- адрес сервера — `cdn.example.ru`;
- порт — 443;
- безопасность — TLS, SNI — `cdn.example.ru`, выбрать fingerprint.

## Если не работает

**Клиент не подключается.** Сверь путь в трёх местах. Потом посмотри, доходят ли
запросы до nginx:

```bash
tail -f /var/log/nginx/xhttp_access.log
```

Пусто — трафик не дошёл до источника, дело в CDN или DNS. Есть записи с кодом
502 — nginx не достучался до Xray, проверь, слушает ли он свой порт.

**Соединение встаёт и рвётся.** Почти всегда буферизация: либо на стороне CDN
включено что-то кеширующее, либо правки в конфиге nginx затронули
`proxy_buffering`.

**Работает, но очень медленно.** Проверь, что в клиенте выбран тот же `mode`,
что в серверном конфиге, и что ядро действительно обновлено — старое молча
откатится на POST, который CDN режет.

## Чего эта схема не делает

Она не поможет, если фильтрация идёт по именам доменов: `cdn.example.ru` не
входит ни в один белый список, и соединение отрежут независимо от того, на чьей
инфраструктуре живёт имя. Схема рассчитана на фильтрацию по адресам, когда
диапазоны российских CDN остаются доступны.

Трафик терминируется на узле Яндекса. Содержимое внутри VLESS остаётся
зашифрованным, но сам факт постоянного потока к одному источнику за рубежом
виден. Использование CDN как транспорта противоречит пользовательскому
соглашению: ресурс могут отключить, аккаунт заблокировать.

## Совместимость с клиентами

XHTTP — транспорт из Xray-core. **sing-box его не поддерживает**, поэтому podkop
на OpenWrt через эту схему не подключится: у sing-box есть `ws`, `grpc`,
`httpupgrade` и `quic`, но ни `splithttp`, ни `xhttp`. Проверить на своём
роутере:

```sh
cat > /tmp/t.json <<'EOF'
{"outbounds":[{"type":"vless","tag":"t","server":"1.2.3.4","server_port":443,
"uuid":"00000000-0000-0000-0000-000000000000",
"transport":{"type":"xhttp","path":"/x"}}]}
EOF
sing-box check -c /tmp/t.json
```

Варианты, если нужен и роутер: поставить рядом с podkop отдельный xray-core и
направить podkop в его локальный SOCKS, либо оставить роутер на WireGuard, а
CDN-канал использовать на телефонах и ноутбуках как запасной путь.
