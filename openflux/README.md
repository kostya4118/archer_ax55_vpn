# Выходной узел OpenFlux на роутере OpenWrt

Задача: попасть в домашнюю сеть с телефона на мобильном интернете, где оператор
пропускает только белый список. OpenFlux встречается с клиентом через публичный
документ mail.ru — а он в белом списке.

Входящий порт при этом не нужен: узел сам ходит наружу. За CGNAT, где проброс
портов невозможен в принципе, это и есть главное свойство.

Побочная выгода: соединения наружу открывает роутер, значит они идут по его
таблице маршрутизации — через podkop с его списками. Телефон вне дома получает
ту же маршрутизацию, что и устройства в квартире.

## Что нужно

- Роутер с OpenWrt, достаточным местом под бинарник (около 25 МБ) и свободной
  памятью. Проверить: `uname -m`, `df -h /overlay`, `free -m`.
- Машина с Go для сборки — сам роутер для этого не годится.
- Свой публичный документ в облаке mail.ru. **Не тот же, что у другого узла:**
  два выходных узла на одном документе будут выталкивать друг друга.

## 1. Сборка под роутер

На машине с Go, в каталоге с исходниками OpenFlux. `GOARCH` берётся из
`uname -m` роутера: `aarch64` → `arm64`, `armv7l` → `arm`, `mips` → `mips`,
`mipsel` → `mipsle`, `x86_64` → `amd64`.

```bash
cd ~/OpenFlux
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -ldflags="-s -w" -o openflux-arm64 .
ls -lh openflux-arm64
```

`-ldflags="-s -w"` выбрасывает отладочные таблицы — файл уменьшается примерно
на треть. Если места совсем мало, поможет `upx --best openflux-arm64`, но тогда
на запуск уйдёт лишняя секунда на распаковку.

## 2. Перенос на роутер

```bash
scp openflux-arm64 root@192.168.1.1:/usr/bin/openflux
scp openflux/openflux.init root@192.168.1.1:/etc/init.d/openflux
```

На роутере:

```sh
chmod +x /usr/bin/openflux /etc/init.d/openflux
mkdir -p /etc/openflux
```

## 3. Ключ и настройки

Ключ генерируется на роутере и **должен совпадать с клиентским**:

```sh
head -c 32 /dev/urandom | hexdump -v -e '/1 "%02x"' > /etc/openflux/secret.txt
chmod 600 /etc/openflux/secret.txt
cat /etc/openflux/secret.txt
```

Настройки:

```sh
cat > /etc/openflux/openflux.env <<'EOF'
TRANSPORT=mailru
URL=https://cloud.mail.ru/public/ВАША/ССЫЛКА
KEYFILE=/etc/openflux/secret.txt
EXTRA_ARGS=
EOF
chmod 600 /etc/openflux/openflux.env
```

Ссылка на документ входит в вывод ключа шифрования, поэтому в клиенте она
должна совпадать **символ в символ**.

## 4. Запуск

```sh
/etc/init.d/openflux enable
/etc/init.d/openflux start
logread -f | grep -i openflux
```

В журнале должно появиться `Running as EXIT NODE`.

## Капча у яндексовых транспортов

Транспорты `yandex` и `vyandex` часто встречают запрос капчей — особенно с
адреса за CGNAT, который делят сотни абонентов. Proof-of-work проверку ядро
решает само, а вот SmartCaptcha требует человека: её нужно кому-то показать, а
на роутере показывать некому.

Штатный обход — поднять несколько транспортов сразу:

```sh
TRANSPORTS=mailru,vyandex
```

вместо `TRANSPORT=`. Тогда рабочий транспорт несёт запрос на проверку до
приложения на телефоне, оно открывает страницу во встроенном браузере и
возвращает cookies, после чего поднимается и второй. Cookies сохраняются в
файл из `--cookie-store` и переживают перезапуск.

Если приложения с поддержкой IPC нет, остаётся только транспорт без капчи.

## Что проверено и не работает

**Начинать стоит с транспорта `yandex`.** Он стоит в справке по умолчанию и
единственный из опробованных поднялся на роутере сразу: публичная ссылка с
Яндекс.Диска, никакой капчи, никаких учётных записей. `mailru` работает, но
упирается в занятый документ (см. ниже), `oneme` требует токен и UID учётной
записи MAX, `vyandex` — капчу.

**Транспорт `vyandex` без приложения не поднимается.** Яндекс отвечает
`auth: yandex docs: captcha required`, и это не зависит ни от адреса, ни от
вида ссылки:

- с домашнего адреса за CGNAT — капча;
- с датацентрового адреса сервера — капча;
- со ссылкой на файл (`/i/...`) и со ссылкой на документ в новом редакторе —
  одинаково;
- капча, решённая в браузере с того же внешнего адреса, не помогает: проверка
  привязана к сессии, а у узла она своя.

Это ровно то, о чём предупреждает инструкция: SmartCaptcha требует показать
страницу человеку, а безголовому узлу показывать некому. Единственный путь —
поднять Волгу вторым транспортом рядом с уже работающим, чтобы приложение
получило запрос через него.

**Один документ mail.ru держит одного участника.** Кто заходит вторым, получает
`409` на подключении веб-сокета. Проверено так: документу дали отлежаться больше
часа, узел вошёл в него чисто и без ошибок — и всё равно клиент с телефона
получил отказ. Версия про брошенные сессии от перезапущенных процессов не
подтвердилась.

Схема требует, чтобы в документе встретились двое, поэтому `mailru` для неё не
подходит. По той же причине с ним невозможно и несколько клиентов.

## 5. Клиент

В приложении на телефоне: транспорт Mail.ru, та же ссылка, тот же ключ.

Если в логе узла появится `the peer sends classic-mode frames ... this side
serves Session peers only`, значит сборка клиента старее и не умеет
согласование сессии. Лечится тем, что узел запускается **без** `--negotiate` —
в классическом режиме он обслуживает и тех, и других. В `EXTRA_ARGS` этот флаг
поэтому и не добавлен по умолчанию.

## Чего ожидать по скорости

Упрётся в исходящий канал домашнего провайдера: у домашних тарифов отдача
обычно заметно уже приёма, а здесь работает именно она. Плюс шифрование и
пользовательский сетевой стек режима l4 на процессоре роутера.

Несколько телефонов одновременно складывают нагрузку. Кроме того, похоже, что
один документ держит одного клиента — для второго телефона нужен отдельный
документ и отдельный экземпляр службы.

## Диагностика

```sh
/etc/init.d/openflux status
logread -e openflux | tail -30
```

`[M-DOCS] connection to the document dropped ... reconnecting` раз в несколько
минут или часов — нормально, долгоживущий веб-сокет периодически рвётся и
восстанавливается сам.

`WebSocket dial failed (http 409)` на стороне клиента означает конфликт за
документ: кто-то ещё в нём сидит. Проверь, не остался ли включённым профиль на
другом устройстве — в iOS он держится, даже когда приложение закрыто.
