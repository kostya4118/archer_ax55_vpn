# Выходной узел OpenFlux на роутере OpenWrt

Задача: попасть в домашнюю сеть с телефона на мобильном интернете, где оператор
пропускает только белый список. OpenFlux встречается с клиентом через публичный
документ mail.ru — а он в белом списке.

Входящий порт при этом не нужен: узел сам ходит наружу. За CGNAT, где проброс
портов невозможен в принципе, это и есть главное свойство.

Побочная выгода: соединения наружу открывает роутер, значит они идут по его
таблице маршрутизации — через podkop с его списками. Телефон вне дома получает
ту же маршрутизацию, что и устройства в квартире.

## Что нужно

- Роутер с OpenWrt, достаточным местом под бинарник (около 25 МБ) и свободной
  памятью. Проверить: `uname -m`, `df -h /overlay`, `free -m`.
- Машина с Go для сборки — сам роутер для этого не годится.
- Свой публичный документ в облаке mail.ru. **Не тот же, что у другого узла:**
  два выходных узла на одном документе будут выталкивать друг друга.

## 1. Сборка под роутер

На машине с Go, в каталоге с исходниками OpenFlux. `GOARCH` берётся из
`uname -m` роутера: `aarch64` → `arm64`, `armv7l` → `arm`, `mips` → `mips`,
`mipsel` → `mipsle`, `x86_64` → `amd64`.

```bash
cd ~/OpenFlux
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -ldflags="-s -w" -o openflux-arm64 .
ls -lh openflux-arm64
```

`-ldflags="-s -w"` выбрасывает отладочные таблицы — файл уменьшается примерно
на треть. Если места совсем мало, поможет `upx --best openflux-arm64`, но тогда
на запуск уйдёт лишняя секунда на распаковку.

## 2. Перенос на роутер

```bash
scp openflux-arm64 root@192.168.1.1:/usr/bin/openflux
scp openflux/openflux.init root@192.168.1.1:/etc/init.d/openflux
```

На роутере:

```sh
chmod +x /usr/bin/openflux /etc/init.d/openflux
mkdir -p /etc/openflux
```

## 3. Ключ и настройки

Ключ генерируется на роутере и **должен совпадать с клиентским**:

```sh
head -c 32 /dev/urandom | hexdump -v -e '/1 "%02x"' > /etc/openflux/secret.txt
chmod 600 /etc/openflux/secret.txt
cat /etc/openflux/secret.txt
```

Настройки. Рабочий на сегодня транспорт — `cupsonline`: ему не нужны ни
документы, ни учётные записи, и он единственный, который поднимается со
сборкой приложения от 7 октября (почему — в [RESEARCH.md](RESEARCH.md)).

```sh
cat > /etc/openflux/openflux.env <<'EOF'
TRANSPORT=cupsonline
URL_FILE=/etc/openflux/rooms.txt
KEYFILE=/etc/openflux/secret.txt
MODE=l4
EXTRA_ARGS=
EOF
chmod 600 /etc/openflux/openflux.env
```

`URL_FILE` вместо `URL` — потому что список комнат у `cupsonline` длиной в
сотни символов, и в командную строку BusyBox он целиком не влезает. Файла
может ещё не быть: при первом запуске узел создаст комнаты сам.

Для транспортов с документом (`mailru`, `yandex`, `boards`, `vyandex`) вместо
`URL_FILE` пишут `URL=` со ссылкой. Она входит в вывод ключа шифрования,
поэтому в клиенте должна совпадать **символ в символ** — даже та часть, которую
сам транспорт не использует.

`MODE=l4` оставлять как есть. Режим `l3` быстрее на бумаге, но на роутере рядом
с podkop он ломает передачу: страницы перестают открываться вовсе.

## 4. Запуск

```sh
/etc/init.d/openflux enable
/etc/init.d/openflux start
sleep 45
logread | grep -iE "openflux|EXIT NODE|COPY THIS" | tail -20
```

В журнале должно появиться `Running as EXIT NODE`, а строкой выше — контекст
шифрования (`Encryption context: sha256 ...`). Если клиент не собирает туннель
молча, первым делом сверяй ссылку: другой контекст — другой ключ.

### Комнаты cupsonline

При запуске без `URL_FILE` (или когда прежние комнаты протухли) узел создаёт
новые и печатает их список между строками `=== COPY THIS TO CLIENT ===`. Его
надо сохранить и отдать клиенту:

```sh
logread | grep -A1 "COPY THIS" | tail -1 > /etc/openflux/rooms.txt
wc -c /etc/openflux/rooms.txt
cat /etc/openflux/rooms.txt
```

Эту строку вставляют в приложении в поле ссылки. После каждого пересоздания
комнат она меняется, и в приложении её надо обновлять — иначе клиент будет
стучаться в комнаты, которых уже нет.

Число комнат задаётся переменной окружения `CUPS_ROOMS` (по умолчанию 4,
потолок 64) — в настройках это строка `ENV`:

```sh
ENV="CUPS_ROOMS=12"
```

В новом, полосном режиме каждая комната несёт свою полосу и отдаёт порядка
130–200 КБ/с, так что число комнат прямо определяет скорость. В старом режиме
оно не значило ничего — мы поднимали с четырёх до десяти без всякого
результата. Разница между режимами видна по формату списка: старый начинается с
`WyI`, новый — с `eyJ2IjoyLCJyb29tcyI6`. Чтобы перейти на новый, комнаты надо
создать заново.

Менять число комнат — значит создавать их заново, то есть менять и строку в
приложении.

## Капча у яндексовых транспортов

Транспорты `yandex` и `vyandex` часто встречают запрос капчей — особенно с
адреса за CGNAT, который делят сотни абонентов. Proof-of-work проверку ядро
решает само, а вот SmartCaptcha требует человека: её нужно кому-то показать, а
на роутере показывать некому.

Штатный обход — поднять несколько транспортов сразу:

```sh
TRANSPORTS=mailru,vyandex
```

вместо `TRANSPORT=`. Тогда рабочий транспорт несёт запрос на проверку до
приложения на телефоне, оно открывает страницу во встроенном браузере и
возвращает cookies, после чего поднимается и второй. Cookies сохраняются в
файл из `--cookie-store` и переживают перезапуск.

Если приложения с поддержкой IPC нет, остаётся только транспорт без капчи.

## Что проверено и не работает

**Начинать стоит с транспорта `yandex`.** Он стоит в справке по умолчанию и
единственный из опробованных поднялся на роутере сразу: публичная ссылка с
Яндекс.Диска, никакой капчи, никаких учётных записей.

Важно, **какой именно документ** за ссылкой. Анониму Яндекс отдаёт настройки
либо с `officeType: only_office`, либо с `officeType: volga` (новый редактор), и
у второй нет поля `balancer_url`, которое нужно транспорту `yandex` — отсюда
ошибка `officeActionData.balancer_url missing`. Поэтому публикуй **файл**
`.docx` или `.xlsx`, лежащий на Диске, а не документ, созданный в новом
редакторе. Для документов на Волге предназначен `vyandex` — но он упирается в
капчу.

`mailru` входит в документ без ошибок, а отказ `409` на стороне клиента
оказался багом старой сборки (см. ниже). `oneme` требует токен и UID учётной
записи MAX и, судя по трекеру, сейчас сломан со стороны MAX.

**Транспорт `vyandex` без приложения не поднимается.** Яндекс отвечает
`auth: yandex docs: captcha required`, и это не зависит ни от адреса, ни от
вида ссылки:

- с домашнего адреса за CGNAT — капча;
- с датацентрового адреса сервера — капча;
- со ссылкой на файл (`/i/...`) и со ссылкой на документ в новом редакторе —
  одинаково;
- капча, решённая в браузере с того же внешнего адреса, сама по себе не
  помогает: проверка привязана к сессии, а у узла она своя.

Это ровно то, о чём предупреждает инструкция: SmartCaptcha требует показать
страницу человеку, а безголовому узлу показывать некому.

**Но это обходится.** Проверено на нашем роутере: если поднять рядом с Волгой
транспорт `direct`, а телефон держать в домашней сети, узел отдаёт SmartCaptcha
приложению, человек решает её на телефоне, и приложение возвращает узлу cookies
(`[app] offered 22 cookies to the exit node`). Дальше они живут в
`--cookie-store` и переживают перезапуск, так что прямой канал нужен один раз.

```sh
EXTRA_ARGS="--vyandex-url=ССЫЛКА --direct-listen=0.0.0.0:9443 -dd"
```
с `TRANSPORTS=direct:100,vyandex:50`, а в приложении — раздел «Прямой канал для
капчи»: адрес `192.168.1.1:9443` и тот же общий секрет (своего ключа у `direct`
нет). Подробности и требования к ссылке — в [RESEARCH.md](RESEARCH.md).

Второй путь, если телефона под рукой нет: `--yandex-cookies-file` принимает
`cookies.txt` в формате Netscape, выгруженный из браузера с входом в Яндекс.

**`409` у клиента в mail.ru — баг рукопожатия, а не занятый документ.** Мы
сначала решили, что документ держит одного участника: узел входил чисто, а
клиент с телефона получал отказ. Оказалось иначе — nginx mail.ru отвечает
`409 Conflict` на WebSocket-апгрейд, если клиент не предложил сжатие
`permessage-deflate`, и этому есть
[issue в проекте](https://github.com/p1neappleXpress/OpenFlux/issues/163).
Исправлено 10 октября в ядре `v0.4.3` и узле `node-v1.2.3`; iOS-сборка из
TestFlight от 7 октября ещё страдала. Значит обновлять надо **обе стороны**:
подробности и порядок действий — в [RESEARCH.md](RESEARCH.md).

## 5. Клиент

В приложении на телефоне: транспорт Yandex Boards, та же ссылка, тот же ключ.

Если в логе узла появится `the peer sends classic-mode frames ... this side
serves Session peers only`, значит сборка клиента старее и не умеет
согласование сессии. Лечится тем, что узел запускается **без** `--negotiate` —
в классическом режиме он обслуживает и тех, и других. В `EXTRA_ARGS` этот флаг
поэтому и не добавлен по умолчанию.

## Чего ожидать по скорости

Упрётся в исходящий канал домашнего провайдера: у домашних тарифов отдача
обычно заметно уже приёма, а здесь работает именно она. Плюс шифрование и
пользовательский сетевой стек режима l4 на процессоре роутера.

Несколько телефонов одновременно подключить не получится: выходной узел
обслуживает одного активного клиента за раз, и второй клиент с тем же ключом
вытесняет первого. Для второго телефона нужен отдельный экземпляр службы со
своим ключом и своим документом.

## Диагностика

```sh
/etc/init.d/openflux status
logread | grep -iE "openflux|boards|EXIT NODE" | tail -30
```

Фильтровать именно так, а не `logread -e openflux`: имя службы в журнале не
появляется, procd помечает строки именем запущенного процесса.

`[M-DOCS] connection to the document dropped ... reconnecting` раз в несколько
минут или часов — нормально, долгоживущий веб-сокет периодически рвётся и
восстанавливается сам.

`WebSocket dial failed (http 409)` на стороне клиента — почти наверняка старая
сборка клиента, а не конфликт за документ: см. раздел про `409` выше. Стоит всё
же заодно проверить, не остался ли включённым профиль на другом устройстве — в
iOS он держится, даже когда приложение закрыто, а узел обслуживает одного
клиента за раз.

## Текущее состояние

**Работает.** С 24 октября телефон подключается через приложение (сборка 113+,
ядро `0.15.1`) к узлу на роутере (тоже `v0.15.1`) по cups.online:

| | Скорость с телефона по мобильному |
|---|---|
| `PODKOP_MARK=0` | 10 МБ за 20 с — около 4 Мбит/с |
| `PODKOP_MARK=1` | около 3 Мбит/с |

Оставлен `PODKOP_MARK=1`: четверть скорости — плата за то, что сайты, которые
дома идут через VPN, открываются и с телефона.

Что лежит на роутере:

- `/usr/bin/openflux` — ядро `v0.15.1` из релиза OpenFluxTeam;
- `/etc/openflux/openflux.env` — `cupsonline`, `RUN_AS=openflux`, `PODKOP_MARK=1`;
- `/etc/openflux/rooms.txt` — список комнат для клиента;
- `/etc/openflux/secret.txt` — ключ;
- пользователь `openflux` (uid 990).

Если роутер сам не достаёт до GitHub (бывает: `Connection timed out`), новое
ядро качается на Mac и заливается через `scp -O` во `/tmp`, а потом
переносится на место — не прямо поверх `/usr/bin/openflux`.

При каждой смене ядра комнаты лучше создавать заново: убрать `rooms.txt`,
запустить службу, забрать строку из `COPY THIS` и вставить её в приложение.

## Если роутер не тянет: узел на сервере

Замер на Archer AX55 под нагрузкой, восемь полос cups.online:

```
CPU:  63% usr  14% sys   0% nic   8% idle
openflux  68%
```

То есть на восьми полосах упор уже в процессор роутера, и добавлять комнаты
бессмысленно. Видео через такой канал не идёт.

На сервере этого упора нет. Перенос, по шагам:

```bash
cd ~/OpenFlux
go build -ldflags="-s -w" -o /usr/local/bin/openflux .
mkdir -p /etc/openflux
head -c 32 /dev/urandom | hexdump -v -e '/1 "%02x"' > /etc/openflux/secret.txt
chmod 600 /etc/openflux/secret.txt

# первый запуск без адреса — узел создаст комнаты и напечатает их список
CUPS_ROOMS=16 /usr/local/bin/openflux --role=exit --mode=l4 \
  --transport=cupsonline \
  --encryption-key-file=/etc/openflux/secret.txt \
  --cookie-store=/etc/openflux/cookies.json > /tmp/of.log 2>&1 &
sleep 90
grep -A1 "COPY THIS" /tmp/of.log | tail -1 > /etc/openflux/rooms.txt
cat /etc/openflux/rooms.txt

kill %1
echo "URL=$(cat /etc/openflux/rooms.txt)" > /etc/openflux/openflux.env
chmod 600 /etc/openflux/openflux.env
cp openflux/openflux.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now openflux
systemctl status openflux --no-pager
```

Список комнат и ключ — в приложение; транспорт тот же, Cups.online.

Трафик при этом выходит с адреса сервера. Чтобы ютуб у телефона шёл без рекламы
через московский выход, добавь службу в уже настроенную схему:

```bash
sudo bash noads-exit/route-service-output.sh openflux.service
```

Узел на роутере после переноса надо остановить, иначе два выхода будут драться
за одни комнаты:

```sh
/etc/init.d/openflux stop
/etc/init.d/openflux disable
```

## Вход в учётную запись для mail.ru

С 15 октября mail.ru закрыл анонимный доступ к публичным документам
([#193](https://github.com/p1neappleXpress/OpenFlux/issues/193)): узел получает
`401`, а с ядра `v0.14.2` — `400` на `fetchDocInfo`. Нужен вход.

Ядро читает его из файла `--cookie-store`. Формат — JSON вида
`{"<ссылка на документ>": {"имя": "значение", ...}}`, где ключ верхнего уровня
ровно та же строка, что стоит в `URL=`.

Порядок:

1. В браузере, где выполнен вход в mail.ru, открыть документ и выгрузить
   cookies расширением вроде «Get cookies.txt LOCALLY» (формат Netscape).
2. Превратить выгрузку в хранилище:

```bash
python3 openflux/cookies-to-store.py cookies.txt \
    --url https://cloud.mail.ru/public/XXXX/YYYY \
    --domain mail.ru --out cookies.json
```

3. Положить файл на узел как `/etc/openflux/cookies.json` с правами 600 и
   перезапустить службу.

Файл — это действующая сессия учётной записи mail.ru: пересылать его нельзя, а
на узле он должен быть доступен только root. С ядра `v0.14.3` узел не отдаёт
свой вход клиентам, так что дальше него он не уходит.

## Чтобы трафик с телефона шёл по спискам podkop

Без этого через туннель в VPN попадает только то, что podkop знает по
**подсетям** (Discord, Telegram, Meta, Twitter и т. п.), а всё, что задано
**доменами**, идёт напрямую. Причина в DNS: podkop заворачивает по доменам через
поддельные адреса `198.18.0.0/15` своего sing-box, а клиенты OpenFlux имена
разрешают у себя — iPhone через DNS-over-TLS напрямую к Яндексу или Google, Mac
системным резолвером, — и до роутера доходят настоящие адреса.

Лечится так: весь исходящий трафик узла помечается меткой podkop (`0x00100000`)
и уходит в sing-box через tproxy. Тот читает имя сайта из самого соединения
(sniff) и раскладывает по тем же спискам, что и трафик домашних устройств, а
не попавшее никуда отправляет в `direct-out`. Соединения самого носителя к
cups.online или mail.ru туда же попадают и уходят напрямую — исключать их не
нужно.

Чтобы отличить соединения узла от всего остального на роутере, узел работает
от своего пользователя. Один раз на роутере:

```sh
grep -E ':990:' /etc/passwd /etc/group      # uid 990 должен быть свободен
echo 'openflux:x:990:990:openflux:/var/empty:/bin/false' >> /etc/passwd
echo 'openflux:x:990:' >> /etc/group
echo 'openflux:*:0:0:99999:7:::' >> /etc/shadow
chown -R openflux:openflux /etc/openflux
chmod 700 /etc/openflux && chmod 600 /etc/openflux/*
```

И в `openflux.env`:

```sh
RUN_AS=openflux
PODKOP_MARK=1
```

Служба сама ставит таблицу `inet openflux_podkop` при старте и снимает при
остановке; перезапуски podkop её не трогают. Проверка:

```sh
nft list table inet openflux_podkop        # счётчик должен расти под нагрузкой
```

Работает это только при `"final": "direct-out"` в конфиге sing-box podkop —
иначе через VPN пойдёт вообще всё. Проверить:
`grep -o '"final": *"[^"]*"' /etc/sing-box/config.json`.
